# CLAUDE.md — Website bán hàng thời trang tích hợp ML

Repo: fashion-recommender-shop — tiểu luận chuyên ngành (IT/Công nghệ phần mềm, HCMUTE), 1 người làm, 15 tuần (10/09/2026–23/12/2026), GVHD: thầy Nguyễn Minh Đạo.

## Kiến trúc & stack

Monorepo, 3 service + 1 CSDL, triển khai qua Docker Compose (1 VPS, không Kubernetes):

- `backend/` — Spring Boot **4.1.1** (Java 21, không phải 3.x — nhiều tên dependency đã đổi, xem "Điểm dễ nhầm" bên dưới), kiến trúc **layered** (package-by-layer, không phải package-by-feature — quyết định có chủ đích, khớp toàn bộ tài liệu đặc tả):
  `controller` (REST, không chứa business logic) → `service` (business logic, `@Transactional`) → `repository` (Spring Data JPA) → MySQL. Cộng thêm `entity`, `dto` (không để entity lộ thẳng ra API), `security` (JWT), `exception` (+ `@ControllerAdvice`), `client` (gọi FastAPI/VNPay), `config`.
- `frontend/` — React + Vite (JavaScript, không TypeScript). Cấu trúc: `pages/` (1 file = 1 route), `components/`, `hooks/` (tiền tố `use`), `services/` (bọc REST API bằng axios — `apiClient.js` dùng chung, base URL đọc `VITE_API_BASE_URL`, mặc định `http://localhost:8080`), `context/`. Định tuyến bằng gói `react-router` v8 (import từ `'react-router'`; `react-router-dom` đã bị gỡ bỏ), khai báo route trong `App.jsx`: `/`, `/products`, `/products/:id`, `/cart`, `/checkout`, `/orders`, `/orders/:id`, `/addresses` (bọc `RequireCustomer`), `/login`, `/register`, `/health`, `/admin/*` (bọc `RequireAdmin`). Đăng nhập: `AuthProvider` (`context/`) + hook `useAuth`; JWT lưu ở `localStorage` kèm thời điểm hết hạn (`services/tokenStorage.js`); `apiClient.js` tự gắn `Authorization: Bearer`, gặp 401 thì xóa token và phát sự kiện để `AuthProvider` đăng xuất. Lỗi API đọc qua `services/errorMessage.js` (ProblemDetail: `detail`, `errors`).
- `ml-service/` — FastAPI, Python **3.13**, quản lý bằng **uv** (`pyproject.toml` + `uv.lock` + `.python-version`; không dùng pip/`requirements.txt`). Package `app/` gồm 2 module: `recommendation/` (content-based filtering, đọc-only) và `segmentation/` (RFM + K-Means, đọc+ghi `account_segment`). Hiện mới có `GET /health` (trả `{"status": "UP"}`, cùng định dạng `/actuator/health`); ML thật làm từ Tuần 8.
- MySQL **8.4**, schema quản lý hoàn toàn bằng **Flyway** — không bao giờ để Hibernate tự tạo/sửa bảng (`spring.jpa.hibernate.ddl-auto=validate`, luôn luôn).

**React không bao giờ gọi thẳng FastAPI** — mọi request kể cả xin gợi ý sản phẩm đều qua Spring Boot (`MlServiceClient` gọi nội bộ sang FastAPI qua mạng Docker). Đây là quyết định kiến trúc đã chốt, không phải thiếu sót.

## Điểm dễ nhầm — đã tốn công phát hiện, đừng lặp lại

- Bảng `order` trong ERD/từ điển dữ liệu **thực ra tên là `orders`** trong migration SQL thật — `order` là từ khóa dành riêng của MySQL (`ORDER BY`), đổi tên ở tầng cài đặt, tài liệu đặc tả cố tình giữ tên gốc `order` vì đó là tên nghiệp vụ đúng. `order_item` không đổi (không xung đột).
- Tương tự, thuộc tính `rank` của lớp `Recommendation` (migration V2) và `ProductEventLog` (V3) lưu ở cột **`rank_position`**: `RANK` là từ khóa dành riêng của MySQL 8 (hàm cửa sổ `RANK()`). Entity khai `@Column(name = "rank_position")`.
- Không bao giờ sửa file migration đã chạy (`V1__...`): Flyway so checksum, sửa file cũ làm mọi máy đã migrate lỗi khi khởi động. Thay đổi lược đồ luôn là file `V<n+1>__...sql` mới.
- Spring Boot 4.x đổi tên nhiều dependency so với 3.x: `spring-boot-starter-web` → `spring-boot-starter-webmvc`. Flyway cần **2 dependency riêng**: `spring-boot-starter-flyway` (bắt buộc để tự chạy migration) + `org.flywaydb:flyway-mysql` (module riêng cho MySQL, không tự có trong starter, không cần `<version>` vì được `spring-boot-starter-parent` quản lý).
- Checkstyle/Spotless là plugin bên thứ ba — **bắt buộc khai `<version>` tường minh** trong `pom.xml`, không như `spring-boot-maven-plugin` (được quản lý version sẵn). Thiếu version → lỗi khó hiểu "No plugin found for prefix"/"plugin absent from the project".
- `google-java-format` (Spotless dùng để format Java) cần cờ JVM `--add-exports` để chạy trên JDK 16+ — đã có sẵn ở `backend/.mvn/jvm.config`, đừng xóa.
- Checkstyle chỉ chặn được build nhờ `<violationSeverity>warning</violationSeverity>` trong `pom.xml`: mọi quy tắc của `google_checks.xml` ở mức warning, còn mặc định plugin chỉ tính mức error. Xóa dòng đó thì vi phạm chỉ còn là cảnh báo, CI vẫn xanh. `pom.xml` cũng chỉ định Checkstyle 14.3.0 vì bản 9.3 mặc định của plugin không đọc được cú pháp Java 21. Checkstyle chạy ở pha `verify`, không chạy khi `spring-boot:run`; kiểm tra nhanh không cần MySQL: `.\mvnw.cmd spotless:check checkstyle:check`.
- Google Style (Checkstyle chặn thật) đòi Javadoc cho **mọi** class và method/constructor public (trừ `@Override`, `@Test`, getter/setter), không riêng Controller/Service — chỗ khác 1 dòng là đủ. Tên có chữ viết tắt viết như 1 từ: `MlServiceClient`, `VnPayClient`, `JwtFilter`. Tài liệu đặc tả/báo cáo ghi `MLServiceClient`, `VNPayClient` là tên khái niệm; lớp Java thật thì đặt theo kiểu trên, đặt `MLServiceClient` là CI đỏ (`AbbreviationAsWordInName`).
- `backend/mvnw` trong git **không có quyền thực thi** (commit từ Windows) — trên Linux (CI, `backend/Dockerfile`) luôn gọi `sh ./mvnw`, đừng đổi thành `./mvnw` (lỗi "Permission denied").
- CI ở `.github/workflows/ci.yml`, chạy trên mỗi PR vào `main` và mỗi commit lên `main`, 6 job: backend (Spotless, rồi `verify` = build + test + Checkstyle, có 1 MySQL 8.4 tạm vì test khởi động cả Spring context), frontend (Prettier, ESLint, build), ml-service (Ruff, pytest), build thử 3 Docker image, SonarQube Cloud (phân tích tĩnh), gitleaks (quét secret). Lệnh trong CI giống lệnh chạy tay ở dưới. `astral-sh/setup-uv` không có tag rút gọn kiểu `@v10`, phải ghi đủ phiên bản.
- SonarQube Cloud (tên mới của SonarCloud) dùng gói Free: chỉ phân tích `main` và PR vào `main`, cổng chất lượng "Sonar way" cố định đòi coverage code mới từ 80%. Từ Tuần 7 có đo độ phủ: JaCoCo chạy trong `verify` (`backend/target/site/jacoco/index.html`), pytest-cov chạy cùng `uv run pytest` (`ml-service/coverage.xml`); 2 job test lưu báo cáo thành artifact, job SonarQube Cloud chờ 2 job đó (`needs`) rồi tải về, nên backend hoặc ml-service đỏ thì Sonar bị bỏ qua. Frontend chưa có test, chưa có độ phủ. Cổng vẫn chỉ để báo cáo: đừng thêm `sonar.qualitygate.wait=true` hay bắt buộc check "SonarCloud Code Analysis". Automatic Analysis trên SonarQube Cloud phải **tắt** (project → Administration → Analysis Method), bật song song là job CI đỏ. Java được phân tích qua file `.class` nên job CI biên dịch backend trước khi quét; thêm thư mục mã nguồn/test mới thì sửa `sonar-project.properties` (ghi thư mục không tồn tại là lần quét lỗi).
- Token SonarQube Cloud chỉ nằm trong secret `SONAR_TOKEN` của repo, không bao giờ ghi vào file (gitleaks có quy tắc riêng bắt token Sonar). Token hết hạn thì job SonarQube Cloud đỏ: tạo token mới rồi cập nhật secret.
- gitleaks quét **toàn bộ lịch sử Git** (checkout `fetch-depth: 0`), nên secret lỡ commit rồi xóa ở commit sau vẫn làm CI đỏ. Gặp secret thật thì coi như đã lộ: (1) vô hiệu ngay ở nơi cấp (token SonarQube Cloud: My Account → Access Tokens → **Revoke**, vì tạo token mới KHÔNG làm token cũ mất hiệu lực; mật khẩu, khóa: đổi giá trị), (2) tạo cái mới, cập nhật GitHub Secret hoặc `.env`, (3) sau đó mới thêm fingerprint gitleaks in ra vào `.gitleaksignore`. Không viết lại lịch sử `main`.
- gitleaks (quy tắc mặc định) chỉ bắt token có định dạng riêng (GitHub, AWS, Sonar...) và chuỗi ngẫu nhiên đứng sau từ khóa như password/secret/token/key. Mật khẩu người tự đặt (`Manh@2004`, `hcmute2026`), chuỗi chỉ có chữ, hay chứa từ thông dụng (`password`, `only`, `shop`...) đều **không** bị bắt, nên `ci_only_password` trong `ci.yml` qua được. Nó cũng không quét `.docx`, ảnh, `package-lock.json`, `mvnw`. gitleaks không thay được quy tắc: secret thật (JWT, VNPay, mật khẩu MySQL) chỉ nằm ở `.env` hoặc GitHub Secrets; báo cáo `.docx` tự kiểm tra trước khi commit. `.gitleaks.toml` (gốc repo) giữ quy tắc mặc định và thêm quy tắc `vnpay-hash-secret` (32 ký tự sau `VNPAY_HASH_SECRET`/`app.vnpay.hash-secret`); thêm khóa mới có định dạng riêng thì thêm quy tắc ở đó.
- Xác thực (Bước 2 Tuần 5): Spring Security + JWT qua `spring-boot-starter-security-oauth2-resource-server` (tên starter của Spring Boot 4; Nimbus có sẵn, không dùng jjwt). Không có lớp `JwtFilter` tự viết: bộ lọc `BearerTokenAuthenticationFilter` dựng sẵn đóng vai trò đó. JWT ký HS256, claim `sub` = account_id, `role` = CUSTOMER/ADMIN, hết hạn 24 giờ. Mọi đường dẫn `/api/admin/**` chỉ cho ADMIN, đặt trong `security/SecurityConfig.java`; API công khai mới (vd xem sản phẩm) phải thêm `permitAll` ở đó, nếu không sẽ trả 401.
- `JWT_SECRET` để trống thì backend tự sinh khóa ngẫu nhiên mỗi lần khởi động (có dòng WARN trong log): mọi token cũ mất hiệu lực sau khi khởi động lại, frontend phải đăng nhập lại. Đặt `JWT_SECRET` (≥32 ký tự) trong `.env` để giữ phiên qua các lần khởi động; ngắn hơn 32 ký tự thì backend không chạy.
- Tài khoản Quản trị viên không đăng ký được qua API (BR-04): đặt `ADMIN_EMAIL`, `ADMIN_PASSWORD` trong `.env`, backend tạo lúc khởi động nếu email đó chưa có tài khoản (không ghi đè mật khẩu nếu đã có).
- Bộ đếm đăng nhập sai (5 lần/15 phút → khóa 15 phút) nằm trong bộ nhớ backend: khởi động lại là xóa hết. Đúng khi chỉ chạy 1 instance backend.
- Lỗi API trả theo chuẩn ProblemDetail (RFC 9457): `{status, title, detail}`, lỗi validate có thêm `errors` (tên trường → thông báo). Thêm exception mới thì khai handler trong `exception/GlobalExceptionHandler.java`.
- Quản lý sản phẩm (Bước 3 Tuần 5): API admin ở `/api/admin/categories`, `/api/admin/brands`, `/api/admin/products` (kèm `/{id}/variants`); `GET /api/categories`, `GET /api/brands` công khai. Xóa sản phẩm luôn là **xóa mềm** (`deleted_at`) và đặt `sku_code` của mọi biến thể về NULL (BR-36); sản phẩm luôn còn ít nhất 1 biến thể; không 2 biến thể trùng tổ hợp giá trị phân loại. Danh mục/thương hiệu chỉ xóa được khi không còn sản phẩm nào (kể cả đã xóa mềm). Collation mặc định của MySQL 8 không phân biệt hoa thường **và dấu**: "Giày" và "giay" bị coi là trùng tên.
- Biến thể theo **phân loại 2 tầng** (migration V3, BR-05), không còn size × màu: `product.variation_name1/2` là tên tầng do admin đặt (NULL = không dùng), `product_variant.option1_value/2` là giá trị; số giá trị của biến thể phải bằng số tầng, sản phẩm không có phân loại có đúng 1 biến thể; số tầng không đổi được sau khi tạo (đổi tên tầng thì được). Chống trùng tổ hợp bằng chỉ mục `uk_product_variant_options` trên `COALESCE(option, '')` (UNIQUE coi các NULL là khác nhau); `ProductVariant.optionKey` so giống collation của MySQL (bỏ dấu, đ → d, không phân biệt hoa thường) để service báo lỗi trước khi chỉ mục chặn. Dòng đơn lưu 1 nhãn `variant_label_snapshot` (vd "Đen – 42"). Lỗi quy tắc phụ thuộc nhiều trường (vd biến thể thiếu giá trị tầng) ném `InvalidRequestException` → 400.
- `recompute_request` (V3) chỉ dùng giờ **UTC**: ghi `due_at`, `created_at` bằng `UTC_TIMESTAMP(3)`, không dùng `NOW()` (đổi theo múi giờ của kết nối); gộp yêu cầu bằng `INSERT … AS incoming ON DUPLICATE KEY UPDATE` (hàm `VALUES()` đã lỗi thời trên MySQL 8.4). Các bảng khác vẫn lưu `LocalDateTime.now()` của JVM.
- Danh mục sản phẩm mẫu (Bước 3 Tuần 6): 1.050 sản phẩm, 42 danh mục chọn từ bộ Tiki trên Kaggle, nằm ở `backend/src/main/resources/seed/tiki-catalog.json`. `CatalogSeedInitializer` nạp file này lúc khởi động **chỉ khi bảng `product` chưa có dòng nào** (kể cả đã xóa mềm), qua `ProductService.create` nên chịu đủ quy tắc như admin tự thêm; lần nạp đầu mất khoảng 15 giây sau dòng "Started"; tắt bằng `CATALOG_SEED_ENABLED=false`. Dữ liệu gốc (.zip) để ở `data/tiki/raw/` (có trong `.gitignore`, không commit); sửa cách chọn thì sửa `ml-service/scripts/build_tiki_catalog.py` rồi chạy lại script, không sửa tay file JSON. Kích cỡ giày, tồn kho, mã SKU là dữ liệu sinh thêm (xem `data/tiki/README.md`). Tên sản phẩm, danh mục, thương hiệu và mô tả sản phẩm luôn lưu ở dạng Unicode **NFC** (chữ dựng sẵn): backend chuẩn hóa khi ghi (`service/TextNormalizer`), script dùng `compose()`; chữ tách dấu (NFD, vd gõ trên macOS) bằng nhau khi so `=` nhưng `LIKE` so từng ký tự nên tìm từ khóa không ra. CSDL dev đã nạp danh mục mẫu trước khi có bước chuẩn hóa này còn 33 tên tách dấu, và việc nạp chỉ chạy khi bảng `product` rỗng: phải nạp lại theo `data/tiki/README.md` (xóa luôn dữ liệu MySQL, kể cả tài khoản).
- Test backend dùng CSDL riêng **`fashionshop_test`** (tự tạo, cấu hình ở `src/test/resources/config/application.properties`, ghi đè `application.properties` chính), không đụng dữ liệu máy dev. File đó cũng tắt nạp danh mục mẫu khi chạy test. Đừng đặt `application.properties` thẳng trong `src/test/resources/`: file cùng tên sẽ che mất file cấu hình chính.
- Trang người dùng (Bước 4 Tuần 6): API công khai `GET /api/products` (từ khóa, lọc, sắp xếp, phân trang), `/api/products/suggestions`, `/api/products/{id}`, `/api/products/{id}/related`, khai `permitAll` trong `SecurityConfig`; `POST /api/products/{id}/views` chỉ cho CUSTOMER (không token 401, ADMIN 403). Số đã bán, điểm đánh giá, giá thấp nhất, vị trí trong danh mục là trường `@Formula` chỉ đọc của `Product` (truy vấn con, không có cột, không cần migration): chỉ có giá trị khi entity được nạp từ SQL, nên test `@Transactional` phải `entityManager.flush(); entityManager.clear();` sau khi chuẩn bị dữ liệu. "Bán chạy" = "phổ biến" = tổng `order_item.quantity` của các đơn khác CANCELLED; bằng nhau thì xếp theo vị trí trong danh mục, nên khi chưa có đơn trang đầu xen kẽ các danh mục. Từ khóa khớp **đầu từ** (`REGEXP_REPLACE` + `LIKE '% từ%'`, collation bỏ dấu): "giay" khớp "Giày", "áo" không khớp "Cao"; xem `ProductSpecifications`. Gợi ý liên quan là bản tạm theo quy tắc (cùng danh mục, thương hiệu, lấp bằng bán chạy) đến khi ml-service làm content-based ở Tuần 8.
- Giỏ hàng (Bước 5 Tuần 6): API `/api/cart` (xem, `items` thêm/sửa/xóa theo `variantId`, `merge`) chỉ cho CUSTOMER; `POST /api/cart/preview` công khai cho giỏ của khách chưa đăng nhập, lưu ở localStorage (`services/guestCart.js`, chỉ mã biến thể + số lượng). Ngay sau khi đăng nhập/đăng ký, `CartProvider` (`context/`, hook `useCart`) gộp giỏ trình duyệt vào giỏ tài khoản rồi xóa nó; lần tải đang chạy được dùng chung để không gộp 2 lần. Mọi API trả về cả giỏ kèm `notices`: đọc giỏ là tự loại dòng ngừng bán/hết hàng và giảm dòng nhiều hơn tồn kho (BR-11), nên GET `/api/cart` có ghi. Tối đa 99 mỗi dòng, 50 dòng; tồn kho chỉ kiểm tra để tham khảo (BR-08). Thao tác ghi qua `TransactionRetry`, khóa dòng `account` trước; thêm vào giỏ ghi `product_event_log` (ADD_TO_CART, chỉ khi đã đăng nhập) và yêu cầu tính lại sau 3 giây.
- Đặt hàng (Bước 6 Tuần 6): `/api/addresses` (sổ địa chỉ, tối đa 10, luôn đúng 1 địa chỉ mặc định; xóa địa chỉ thì `orders.address_id` về NULL, đơn giữ bản sao BR-29) và `/api/orders` (`GET /preview`, `POST` đặt hàng, `GET` danh sách/chi tiết, `POST /{id}/cancel`), chỉ CUSTOMER. Đơn gồm toàn bộ giỏ hàng; COD hoặc ONLINE (VNPay, xem dưới). Chống bán vượt kho (BR-08): khóa tài khoản rồi khóa các biến thể bằng `ProductVariantRepository.findAllForUpdate` (SELECT … FOR UPDATE, mã tăng dần, hủy đơn cũng khóa theo thứ tự này) trước khi đọc tồn kho; thiếu hàng thì 409 cả đơn. `idempotencyKey` trùng của cùng tài khoản trả 200 kèm đơn cũ (BR-10). `expectedTotal` (tổng khách thấy ở bước xem trước) khác tổng hiện tại thì 409. Phí ship 30.000đ, miễn phí từ 500.000đ (`OrderService.shippingFeeFor`, BR-35). Entity đơn tên `Order` (bảng `orders`), JPQL viết `Order` vẫn chạy. Admin quản lý đơn (Bước 7, US-17): `/api/admin/orders` (lọc `status`, `keyword` = mã đơn/email/SĐT), `GET /{id}`, `PUT /{id}/status`; chỉ chuyển sang trạng thái kế tiếp (`OrderStatus.next()`) hoặc CANCELLED khi đơn chưa DELIVERED (kể cả SHIPPING, BR-13), hủy thì hoàn kho qua `OrderService.restoreStock`; khóa tài khoản đặt đơn trước như phía khách. Sang DELIVERED ghi yêu cầu RECOMMENDATION + SEGMENT_ASSIGN, sang CANCELLED ghi RECOMMENDATION. Trang `/admin/orders`, `/admin/orders/:id`; phần thân đơn dùng chung `components/OrderContent.jsx`.
- Thanh toán VNPay (Bước 8 Tuần 6, sandbox, phiên bản 2.1.0): `VNPAY_TMN_CODE`, `VNPAY_HASH_SECRET` trong `.env` (để trống thì chỉ COD, `onlinePaymentAvailable=false`; đặt ONLINE thì 400). Ký HMAC-SHA512 trên tham số sắp xếp theo tên, mã hóa URL kiểu `+` cho dấu cách (`client/VnPayClient`); `vnp_Amount` = tổng × 100; `vnp_TxnRef` = mã đơn + giờ Việt Nam lúc tạo link (lưu `orders.payment_txn_ref`, migration V4). `POST /api/orders/{id}/payment-url` (CUSTOMER) tạo link hết hạn sau 15 phút hoặc đúng hạn đơn; `GET /api/payments/vnpay/return` (trang `/payment/vnpay-return` gọi) và `/ipn` (VNPay gọi, chỉ tới được khi backend có địa chỉ công khai) công khai, cùng xử lý qua `PaymentService.handleCallback`, chạy lại nhiều lần vẫn đúng. Đơn ONLINE chưa trả quá 30 phút tự hủy (BR-34, quét mỗi 5 phút); admin không chuyển trạng thái được khi chưa PAID. Hủy đơn đã PAID (khách, admin, hoặc tiền về sau khi đơn đã hủy) tạo `refund` PROCESSING; `PaymentJobs` gọi API hoàn tiền VNPay mỗi phút, tối đa 3 lần rồi FAILED; admin lọc `refundStatus=FAILED`, chuyển khoản tay rồi `PUT /api/admin/orders/{id}/refund/complete`. Mọi đường hủy đơn đi qua `OrderService.cancelWithPayment`. Lịch chạy bật bằng `app.scheduling.enabled` (test tắt, gọi thẳng `PaymentService`/`RefundService`). Backend chạy trên máy không đọc `.env`: nạp biến vào PowerShell trước khi `spring-boot:run`.
- Yêu cầu tính lại (BR-20) chỉ ghi qua `RecomputeRequestService.request`: gom theo giao dịch, ghi ở `beforeCommit` của giao dịch ngoài cùng bằng `NamedParameterJdbcTemplate` (không qua EntityManager, để không flush sớm và giữ exception đã dịch của Spring); gọi ngoài giao dịch đọc-ghi là lỗi. Thao tác ghi đồng thời của người dùng (lượt xem, sau này giỏ hàng, đặt hàng) chạy qua `TransactionRetry`: giao dịch riêng, chạy tối đa 3 lần (lần đầu + 2 lần thử lại, BR-08) khi MySQL báo 1213/1205, không gọi được bên trong giao dịch khác. Test về yêu cầu tính lại không được `@Transactional` (giao dịch rollback thì `beforeCommit` không chạy), tự xóa dữ liệu ở `@AfterEach`. Ngưỡng lượt xem BR-19: số `product_id` khác nhau có `viewed_at` trong 30 ngày (giờ JVM backend), kể cả sản phẩm đã xóa mềm; "đơn hoàn tất" = DELIVERED; lượt xem vừa đạt ngưỡng đến hạn sau 3 giây, còn lại 5 phút.
- Với entity đã được quản lý trong transaction (vừa `findById`), gọi `repository.flush()` chứ không `saveAndFlush(entity)`: `save` trên entity không mới chạy `merge`, trả về **bản sao**, các con vừa thêm vào object gốc (vd biến thể mới) sẽ không có id.
- Staging (Tuần 7): máy ảo Azure for Students (East Asia, `Standard_B2als_v2` 2 vCPU/4 GB, Ubuntu 24.04, user `azureuser`), cấu hình ở `deploy/staging/` (compose kéo image từ GHCR + Caddy tự HTTPS; chỉ Caddy mở cổng 80/443; `/api/*` và `/actuator/health` sang backend, còn lại sang frontend, nên frontend staging build với `VITE_API_BASE_URL` = tên miền staging). Job CI `deploy` chạy sau mỗi commit vào `main` (hoặc Run workflow trên `main`): build 3 image tag mã commit, đẩy lên `ghcr.io/ngocmanhnct/fashion-recommender-shop/*`, SSH bằng khóa riêng của CI chép `docker-compose.yml` + `Caddyfile` sang `~/fashionshop/` rồi `pull` + `up -d`, chờ health trả UP. Biến/secret nằm ở environment `staging` của repo (`STAGING_DOMAIN`, `STAGING_HOST`; `STAGING_SSH_KEY`, `STAGING_SSH_KNOWN_HOSTS`); secret ứng dụng chỉ ở `~/fashionshop/.env` trên máy ảo (mẫu `deploy/staging/.env.example`). Máy ảo chỉ 4 GB: backend giới hạn 1 GB, có 2 GB swap. Hết credit thì Azure dừng máy, không tính tiền.

- CORS có 2 chỗ tách biệt: `config/WebConfig.java` chỉ áp dụng cho controller thường; endpoint Actuator (`/actuator/*`) có CORS riêng qua `management.endpoints.web.cors.*` trong `application.properties`. Cả 2 dùng chung danh sách origin `app.cors.allowed-origins` (biến môi trường `CORS_ALLOWED_ORIGINS`).
- Frontend dùng ESLint 10 — **chưa dùng `eslint-plugin-react`** vì bản ổn định mới nhất chưa hỗ trợ ESLint 10 (cài sẽ lỗi ERESOLVE). Đừng ép cài bằng `--legacy-peer-deps`.
- Trang React hiện "Network Error" cho **cả** lỗi CORS lẫn backend không chạy — đọc Console trình duyệt mới phân biệt được.
- Mỗi service chỉ chạy ở đúng 1 nơi (không vừa IntelliJ vừa terminal) — tránh "Port 8080 was already in use". IntelliJ có thể dùng JDK riêng: trước khi commit, kiểm tra bằng `.\mvnw.cmd clean spring-boot:run`.

- Chạy cả stack bằng Docker thì tắt backend/ml-service đang chạy trên máy trước (trùng cổng 8080; MySQL 3306 dùng chung được).

- Test FastAPI cần `httpx2` (TestClient của Starlette đã bỏ `httpx`) và `pythonpath = ["."]` trong `[tool.pytest.ini_options]` — cả hai đã có sẵn, đừng xóa.
- Tiền: luôn BIGINT, đơn vị VNĐ, số nguyên — không bao giờ dùng kiểu số thực (tránh sai số làm tròn).
- Snake_case cho cột CSDL, camelCase cho field Java — Spring Data JPA tự ánh xạ qua `CamelCaseToUnderscoresNamingStrategy`, không cần `@Column(name=...)` thủ công trừ khi tên lệch nhiều hơn quy tắc mặc định.

## Quy ước code (tóm tắt — đầy đủ ở `docs/coding-convention.md`)

- Java: Google Java Style (Checkstyle) + `google-java-format` (Spotless). Chạy `.\mvnw.cmd spotless:apply` trước khi commit (trong `backend/`). Javadoc bắt buộc cho mọi class và method public (Checkstyle chặn); Controller/Service viết đầy đủ, chỗ khác 1 dòng.
- React: ESLint 10 flat config (`recommended` + `react-hooks` + `react-refresh` + `eslint-config-prettier` đặt cuối; KHÔNG dùng Airbnb config) + Prettier (`printWidth: 100`, `singleQuote: true`, `semi: true`, `trailingComma: "es5"`). Chạy `npx prettier --write .` và `npx eslint .` (trong `frontend/`) trước khi commit.
- Python: PEP 8 + Ruff (`line-length = 100`, thêm rule sắp xếp import `I`); docstring cho mọi package (`__init__.py`) và hàm endpoint. Chạy `uv run ruff format .` và `uv run ruff check .` (trong `ml-service/`) trước khi commit.
- Tên: Java/React — PascalCase cho class/component, camelCase cho method/biến/hook (tiền tố `use`), UPPER_SNAKE_CASE cho hằng số; Python — snake_case cho hàm/biến/module, PascalCase cho class.

## Lệnh hay dùng

Mỗi công cụ tìm 1 file riêng ngay trong thư mục đang đứng: `docker compose` và `git` → gốc repo; `mvnw` → `backend/`; `npm`/`npx` → `frontend/`; `uv` → `ml-service/`.

```powershell
# Backend (chạy trong backend/)
.\mvnw.cmd spring-boot:run
.\mvnw.cmd clean spring-boot:run   # build lại từ đầu, giống CI
.\mvnw.cmd spotless:apply
.\mvnw.cmd verify                  # như CI: build + test + Checkstyle (cần MySQL đang chạy)

# Cả 4 container (chạy ở gốc repo): frontend http://localhost:3000, backend :8080
docker compose up -d --build
docker compose ps                                           # cả 4 phải Up, 3 cái có (healthy)
docker compose exec backend curl -s http://ml-service:8000/health   # backend gọi ml-service
docker compose logs -f backend
docker compose down                                         # thêm -v là XÓA luôn dữ liệu MySQL

# Chỉ MySQL, còn 3 service chạy trên máy để code (chạy ở gốc repo)
docker compose up -d mysql
docker compose exec mysql mysql -uroot -p<mật khẩu trong .env> fashionshop -e "SHOW TABLES;"

# Quét secret bằng gitleaks qua Docker (chạy ở gốc repo). Image ghim theo digest, chỉ đọc, không mạng.
# Sau `git add`, trước `git commit`: quét phần đã stage (file chưa commit không được lệnh thứ 2 thấy)
docker run --rm --network none -v "${PWD}:/repo:ro" zricethezav/gitleaks:v8.30.1@sha256:c00b6bd0aeb3071cbcb79009cb16a60dd9e0a7c60e2be9ab65d25e6bc8abbb7f git --staged /repo --no-banner --redact -v
# Giống CI: toàn bộ lịch sử Git, mọi nhánh trên máy
docker run --rm --network none -v "${PWD}:/repo:ro" zricethezav/gitleaks:v8.30.1@sha256:c00b6bd0aeb3071cbcb79009cb16a60dd9e0a7c60e2be9ab65d25e6bc8abbb7f git /repo --no-banner --redact -v

# Frontend (chạy trong frontend/)
npm run dev
npx prettier --write .
npx eslint .

# ML service (chạy trong ml-service/)
uv sync                          # sau khi clone: tạo .venv đúng phiên bản trong uv.lock
uv run fastapi dev app/main.py   # http://localhost:8000/health — tài liệu API: /docs
uv run pytest
uv run ruff format .
uv run ruff check .
uv run python scripts/build_tiki_catalog.py   # dựng lại danh mục mẫu từ data/tiki/raw (data/tiki/README.md)
```
